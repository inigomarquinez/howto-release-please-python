# howto-release-please-python

🧪 POC to use Google's [release-please](https://github.com/googleapis/release-please) github action to create releases in a python service.

This repository is a minimal, self-contained example. It mirrors the release setup used by our Node services (`lib-volare`, `poc-astro-cms`, `web-esim-holafly`) but with `release-type: python`.

## What it demonstrates

- A tiny FastAPI service (`GET /` and `GET /health`).
- Conventional Commits enforced on pull request titles.
- Automated release PRs generated by release-please on every push to `main`.
- Automatic version bump in `pyproject.toml` and `src/howto_release_please_python/__init__.py`.
- Automatic `CHANGELOG.md`, git tag (`vX.Y.Z`) and GitHub Release when the release PR is merged.
- A post-release hook where build/deploy/notify steps would be added.


## How the release flow works

```text
feature branch ──► PR (title: "feat: ...") ──► merge to main
                                                    │
                                                    ▼
                                      release-please opens/updates
                                      a draft PR: "chore: release 0.1.0"
                                                    │
                                       mark ready + merge
                                                    │
                                                    ▼
                         tag v0.1.0 + GitHub Release + CHANGELOG.md
                         + version bump in pyproject.toml and __init__.py
```

1. Every push to `main` runs `.github/workflows/release.yaml`.
2. release-please reads the Conventional Commits since the last release and opens (or updates) a draft release PR.
3. The release PR bumps the version, updates `CHANGELOG.md` and updates both version sources.
4. Merging the release PR creates the git tag and the GitHub Release.
5. The `post-release` job runs only when a release was created. That is where a real service would build an image, deploy it or send a notification.

Version bumps follow Semantic Versioning:

| Commit / PR title | Bump |
| --- | --- |
| `fix: ...` | patch |
| `feat: ...` | minor |
| `feat!: ...` or `BREAKING CHANGE:` footer | major |

## Run locally

Requires Python 3.12+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

ruff check .
ruff format --check .
pytest

uvicorn howto_release_please_python.app:app --reload
```

Then open <http://127.0.0.1:8000>.

With Docker:

```bash
docker build -t howto-release-please-python .
docker run --rm -p 8000:8000 howto-release-please-python
```

## Bootstrap the POC on GitHub

This repository was initialized locally only. To publish it:

```bash
# From this directory
git remote add origin git@github.com:<your-user>/howto-release-please-python.git
git push -u origin main
```

Repository description:

> POC to use Google's release-please github action to create releases in a python service

Then configure the repository:

1. **Settings → Actions → General → Workflow permissions**: select **Read and write permissions**.
2. Enable **Allow GitHub Actions to create and approve pull requests**. Without this, release-please cannot open its release PR with `GITHUB_TOKEN`.
3. If `main` is protected, allow the `github-actions[bot]` to push and open PRs (or add the release PR to the bypass list).

The first push includes a `feat:` commit, so release-please will immediately open a draft PR for `0.1.0`.

## Python-specific notes

- `release-type: python` is the only difference from our Node services.
- release-please updates the version in `[project].version` in `pyproject.toml`.
- Because the distribution name is `howto-release-please-python`, release-please also finds and updates `__version__` in `src/howto_release_please_python/__init__.py`.
- The initial version is `0.0.0` in both `.release-please-manifest.json` and the source files. The first `feat` release therefore becomes `0.1.0`.
- No Node.js, npm or pnpm is required in this repository; the release tooling runs entirely as a GitHub Action.
